# /project-build — 開発（実装と検査を分ける）

依頼：$ARGUMENTS

## 工程
1. **既存の調査**：対象リポジトリの構成、README、既存のテスト・ビルド方法、`git status`（未コミットの変更があれば触らずに報告）。`AI_Hub/01_Projects/{プロジェクト}/` の過去の決定事項を読む
2. **要件定義**：何ができれば完成か（受け入れ条件）を箇条書きにする。曖昧で作り直しになる点だけ持ち主に確認する
3. **設計と計画**：変更するファイル、データ構造、影響範囲、テスト方法。大きな変更は計画を持ち主に見せてから始める
4. **作業ブランチ**：既存プロジェクトでは `git switch -c feature/...` で作業する。既存ファイルを消す・大きく書き換えるときは先に確認する
5. **実装**：小さな単位で。秘密情報はコードに入れず環境変数や .env（Git 管理外）に
6. **検証（VERIFY）**：テスト・型チェック・リンター・ビルドを実際に実行し、結果をそのまま記録する。テストがなければ最低限のテストを追加する
7. **独立検査（REVIEW）**：technical-qa に検査させる（実装した自分は検査しない）
8. **修正（IMPROVE）**：重大な指摘を直して再検証。修正は2回まで
9. **報告（FINALIZE）**：変更内容、実行した検証と結果、検査の判定、残った課題。push・デプロイは持ち主の承認後
10. **保存**：設計上の決定や、はまった問題と解決策は `/remember`（`02_Knowledge/Technical/` かプロジェクトのノート）

## 特記事項
- 取引BOT（FRED・Bookmap BOT）は、分析・シミュレーション・ペーパートレードまで。実際の注文を出すコードを有効にする・APIキーで本番口座に接続する操作は、持ち主が自分で行う
- データベースのマイグレーションは、既存データを壊さない手順（バックアップ・ロールバック方法）を先に示す
